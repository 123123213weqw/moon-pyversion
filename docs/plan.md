# Moon PyVersion — 大项目规划

> 目标：把项目从"版本字符串比较器"做成 **MoonBit 的离线 Python 打包元数据工具库**，
> 让"消费 Python 生态元数据"这条链路在 MoonBit 里整段可用。
>
> 本文是施工计划；每项能力的现状标注沿用 [roadmap.md](roadmap.md) 的
> `[已有]` / `[计划]` 约定。

## 1. 为什么是这个方向

审核意见是"实现太窄"。窄在哪已经量化过：立项时 876 行源码、8 个公开函数，
申报书承诺的三个场景里**两个跑不通**（真实 `Requires-Dist` 原文和真实 wheel
文件名都会被拒）。M1–M5 完成后这条缺口已补齐：需求行与真实 wheel/sdist
文件名都能解析，语料里 600 条真实 `Requires-Dist` 与 900 个真实分发文件名
全部对照通过。

但**不能靠"多写几个函数"解决**，那只是把窄的地方铺开一点。真正的缺口是：
MoonBit 想消费 Python 生态（离线镜像、锁文件、包元数据）时，从"一条依赖声明"
到"这个版本是否可用"之间**每一环都得手写**。把这整段补齐，项目才有独立的
存在价值，也才配得上"基础库"的定位。

## 2. 做成什么

**一个库 + 一个工具**：

- **库**：`123123213weqw/moon_pyversion`，零第三方依赖，覆盖
  PEP 440 / 503 / 508 / 566 + wheel 文件名规范；
- **工具**：一个命令行示例程序（`examples/`），读一份真实的项目元数据，
  输出"越界依赖 + 不适用的依赖"报告。**这是"项目"和"库"的区别**：
  审核方能看到端到端跑起来的东西，而不是只能看 API 列表。

| 门禁 | 命令 | 标准 |
| --- | --- | --- |
| 四后端 | `moon check/build/test/run` × wasm/wasm-gc/js/native | 全通过，`--deny-warn` |
| 后端一致 | `python -B tools/target_parity.py` | 同平台字节一致；跨平台规范换行后内容一致，并保留原始摘要 |

### 差分语料同步扩展

现有 harness 不重写，只加记录类型——**换的是被测代码，不是验证方法**：

| 新记录 | 内容 | 对照的 packaging API | 服务于 |
| --- | --- | --- | --- |
| `canon` | 名称串 / 版本串 → 规范化结果（两种形式） | `canonicalize_name` / `canonicalize_version` | M1 |
| `file` | 分发文件名 → (name, version, build, tags) | `parse_wheel_filename` / `parse_sdist_filename` | M1 |
| `req` | 需求行原文 → (name, extras, 约束规范化串, marker, url) | `Requirement` | M2 |
| `marker` | 标记原文 + 环境表 → 布尔 | `Marker.evaluate(env)` | M3 |
| `license` | 许可证表达式原文 → 规范化结果 | `canonicalize_license_expression` | M5 |
| `toml` | TOML 文档 → 接受/拒绝 + 重序列化后重新解析 | 参考实现 `tomli` | M4 |
| `meta_divergence` | 声明分歧的样例名与参考实现的方向（输入，非断言） | — | M6 |
| `meta` | METADATA 原文 → 裁决 + 错误码 + 规范重排 | `Metadata.from_email(validate=True)`（+ 声明分歧） | M6 |
| `index_dir` | 目录清单 → 识别出的分发（名称、版本、类型、文件名，按序） | 规范（`parse_sdist/wheel_filename` + 排序规则） | M7 |
| `resolve` | 需求 × 标签 × 解释器 × 预发布策略 → 保留清单与逐条拒绝原因 | 用 `packaging` 重写的候选选择与排序 | M7 |

真实语料**几乎免费**：`tools/fetch_pypi_corpus.py` 已经在抓 `Requires-Dist` 原文，
PyPI JSON 的 `urls[].filename` 直接给出真实分发文件名、`requires_dist` 给出真实
需求行。只需在现有脚本里多写三个输出数组。

## 5. 施工顺序与提交策略

每个里程碑**一个提交**（会拆成 2 个的写 2 个），提交信息写清"新增能力 +
验收证据数字"。已完成的顺序是 M1 → M2+M3 → M4 → M5：

- **M1 先做**，因为它无依赖、且能立刻让场景 2 端到端跑通（可见收益最快）；
- **M3（markers）风险最高**单独成阶段，如果与 packaging 存在无法对齐的语义，
  如实记录为边界，不掩饰；
- **M4/M5 提前**：`METADATA` 与锁文件都要先能读 TOML，许可证又有独立的参考
  实现可对照，先做这两块能让后面的 `metadata.mbt` 直接复用；
- **M7 已完成**：`index.mbt` 让场景 2 从"能解析文件名"变成"能从索引或目录里
  选出可安装的那个文件，并说清其余为什么不行"；
- **M9 最后**，它是把前面所有能力串成"可运行项目"的那一步。

每完成一个里程碑：更新 [roadmap.md](roadmap.md) 的 `[已有]` 标注，
**并且只有到那时**才按实际能力改写 `proposal.md` 的场景与"不做范围"两节。

## 6. 明确不做（保持边界，防止范围失控）

- 不做 pip；不联网、不下载、不安装；
- 不做依赖求解、候选生成、冲突回溯；
- 不做平台兼容性标签的**计算**（不探测宿主平台与 glibc）：标签表由调用方按 `sys_tags()` 顺序传入，库用它做候选的匹配与排序（这一项在 M7 已实现）；
- 不读运行时真实解释器环境（marker 求值只接受调用方传入的环境表）；
- 不提供 SemVer 兼容层；不为任意 legacy 字符串提供候选接口；
- 不评估升级的安全性或 API 兼容性。

## 7. 已知边界（写清楚，不假装没有）

- 名称规范化与 wheel 名称校验按 ASCII 实现；packaging 在这两处用 Unicode
  感知的正则。真实 wheel 文件名按 PEP 427 必须是 ASCII 转义形式，因此实际
  使用不受影响，但这是与 packaging 的**已知差异**，会在差分语料里避开并在
  设计文档中标注。
- oracle 固定在 `packaging 26.3`；旧版本差异按原因分类统计，不隐藏。

## 8. 风险与应对

| 风险 | 应对 |
| --- | --- |
| marker 语义最复杂（版本型 vs 字符串型比较） | 单独阶段；语料优先覆盖；先做最小可用求值器 |
| `Requirement` 需要约束规范化排序，而现有 `SpecifierSet` 保持输入顺序 | 为规范化输出单独提供函数，不改现有顺序语义 |
| 语料里 marker 需固定环境才能复现 | 固化环境表写进语料，四后端共用 |
| 范围膨胀（求解、平台标签"顺手"加进来） | 严格按第 6 节卡住 |
| 申报书再次与实现脱节 | 只在里程碑完成后改 `proposal.md`，`[已有]/[计划]` 标注保留到全绿 |
